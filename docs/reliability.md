# Отказоустойчивость (этап 5)

## 1. Что защищаем

Доступность сервиса сокращения ссылок. Ключевые операции — редирект `GET /r/{code}` и управление ссылками через `/api/links` — должны переживать отказ узла базы данных или узла брокера сообщений. Стенд учебный, работает на одном хосте, поэтому все механизмы проверяются демо-скриптами локально: отказ создается искусственно, восстановление наблюдается и измеряется.

## 2. Отказоустойчивость СУБД

**Схема.** PostgreSQL 17 в конфигурации primary/replica:

- primary (`shortlink-postgres-primary`) — принимает записи от api и worker;
- replica (`shortlink-postgres-replica`) — горячий standby: при первом старте снимает базовую копию через `pg_basebackup` (`deploy/pg/replica-entrypoint.sh`), дальше догоняет primary по асинхронной streaming-репликации с фиксированным слотом `replica_1`. Репликация разрешена только отдельной роли `replicator` — это прописано в `deploy/pg/hba_primary.conf`, никакая другая роль слоты не откроет.

**Сценарий отказа и переключения** (демо `demo/db_failover.sh`):

1. **Обнаружение.** Healthcheck контейнера (`pg_isready`) роняет primary в unhealthy, api перестаёт проходить `GET /healthz` и отдаёт 503 — деградация видна снаружи сразу, а не по таймаутам запросов.
2. **Promote реплики.** `docker stop postgres-primary`, затем на реплике выполняется `pg_ctl promote` — она становится доступной для записи.
3. **Переключение клиентов.** api и worker перезапускаются с `DATABASE_URL`, указывающим на реплику; сервис восстанавливается без потери данных (с оговоркой про RPO ниже).

**Честное ограничение.** Переключение ручное — его делает скрипт по команде человека. Автоматического failover (patroni, repmgr) нет: для учебного стенда осознанно выбрана простота и наблюдаемость сценария вместо автоматизации, которую на одном хосте всё равно не проверить реалистично.

## 3. Отказоустойчивость брокера

**Схема.** Кластер RabbitMQ 4.1 из трёх узлов (`shortlink-rabbitmq1-3`):

- peer discovery `classic_config` — состав кластера фиксирован конфигом, никаких внешних сервисов обнаружения;
- политика `pause_minority` — при сетевом разделении узлы, оказавшиеся в меньшинстве, останавливаются, а не пытаются обслуживать записи. Это защита от split-brain: двух «голов» с расходящимся состоянием не возникает;
- очередь `link.clicked` — **quorum**: реплицируется на все узлы, кворум 2 из 3, поэтому переживает отказ одного узла без потери сообщений.

**Клиенты.** api и worker получают адреса всех трёх узлов (`RABBIT_ADDRS=rabbitmq1:5672,rabbitmq2:5672,rabbitmq3:5672`) и при разрыве соединения переподключаются к следующему живому узлу.

**Демонстрация.** `demo/broker_failover.sh`: останавливается один узел кластера — поток кликов (302-редирект → событие → инкремент счётчика) продолжает работать, очередь обслуживается кворумом из двух узлов.

## 4. Резервное копирование

- Формат: `pg_dump` — логический дамп, переносим между версиями и конфигурациями PostgreSQL.
- Сценарий восстановления (демо `demo/backup_restore.sh`): делаем дамп → `DROP TABLE` ссылок → восстанавливаемся из дампа → ссылки и счётчики на месте. Восстановление проверяется, а не предполагается.
- Частота: раз в сутки (по cron на хосте) плюс ручной дамп перед каждым изменением схемы — миграции в учебном проекте меняются часто, и откат до «проверенной» схемы должен быть быстрым.

Бэкапы — защита от логических ошибок (случайный `DROP`, неудачная миграция), репликация — от отказа узла. Механизмы дополняют друг друга: реплика честно повторит и `DROP TABLE`, дамп — вернёт данные.

## 5. Параметры надёжности

Значения выбраны для учебного стенда на одном хосте и проверены демо-скриптами; выдуманной точности здесь нет.

| Параметр | Значение | Обоснование |
|---|---|---|
| RPO | ≈ 0–5 с | Репликация асинхронная: на стенде отставание WAL обычно меньше секунды, но при пиковой нагрузке возможны секунды. Потеря при отказе ограничена этим окном |
| RTO | ≈ 1–2 мин | Ручной promote + перезапуск api/worker. Измерено в `demo/db_failover.sh`: почти всё время занимает обнаружение и ручные действия |
| MTTR (БД) | ≈ 2 мин | Совпадает с RTO: восстановление БД и есть переключение на реплику |
| MTBF | Не прогнозируем честно для учебного стенда | Ориентир — наработка на отказ одиночного инстанса PostgreSQL/RabbitMQ: месяцы; лёгкие отказы на стенде обычно связаны с хостом, а не с ПО |
| SLO доступности API | 99% | Учебный стенд на одном хосте с плановыми рестартами после каждого этапа; 99.9%+ требует нескольких хостов, чего в проекте нет |
| SLO на редирект | p95 < 50 мс из кэша / < 150 мс из БД | Теплый путь — Redis в той же internal-сети; холодный — PostgreSQL. Проверяется последовательными `curl -i /r/{code}` по заголовку `X-Cache` |

## 6. Что улучшится в проде

- **Автофейловер БД**: patroni (или repmgr) с etcd — promote реплики и переключение клиентов за секунды без человека.
- **Физические бэкапы и WAL-архив**: pgbackrest вместо ежедневного `pg_dump` — инкрементальные копии, PITR (восстановление на момент времени) и меньшее RPO для логических ошибок.
- **Мониторинг**: Prometheus + Grafana — метрики api/worker, лаг репликации, состояние кворума очередей.
- **Alerting**: алерты на 503 в `/healthz`, рост лага репликации, потерю кворума RabbitMQ и отсутствие свежего бэкапа — чтобы об отказе узнавали системы, а не пользователи.
